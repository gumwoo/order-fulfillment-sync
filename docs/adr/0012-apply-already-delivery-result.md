# ADR-0012 이미출고 성공은 우리 주문 라인에 바로 반영한다

- 상태: 채택
- 날짜: 2026-11-12

## 맥락
ADR-0009는 이미출고로 클레임이 철회된 경우를 미해결로 남겼다.
- 샵바이 주문 상태가 이미 배송중이면 철회를 알리는 변경이 앞으로 가지 않는다. 웹훅만으로는 우리 쪽 클레임을 지우지 못했다.

데모에서 그대로 드러났다.
- 출고완료(배송중) 주문 3건에 고객 취소를 넣었다.
- 회수 목록은 생겼지만 대사가 `CLAIM_MISMATCH` 2건을 계속 냈다.
- 시나리오로 다시 만들어 보니 웹훅 유실과 상관이 없었다. 웹훅이 와도, 재조회로 다시 받아도 우리 라인에 `CANCEL_REQUEST`가 남았다.
  - 철회 변경은 주문 상태와 단계 시각이 그대로이고 클레임만 비어 있다.
  - 상태 우선순위 규칙(ADR-0003)은 "클레임 정보가 빠진 변경으로 기존 클레임을 지우지 않는다". 그래서 오래된 변경(STALE)으로 버렸다.
  - 이 규칙은 순서가 뒤집혀 늦게 온 웹훅이 진행 중인 클레임을 지우지 않게 하려는 것이다.

## 결정
- 취소 처리(ADR-0009)의 이미출고 단계에서 호출이 성공하면, 그 결과를 같은 트랜잭션에서 우리 주문 라인에 반영한다.
  - external-facts.md에 확인된 결과는 "클레임 철회 후 배송중"이다.
  - 라인의 현재 클레임이 이 claimNo일 때만 반영한다. 클레임을 지우고, 배송 전 상태면 배송중으로 올리며, 송장이 있으면 넣는다.
  - 이력에는 source `ALREADY_DELIVERY`로 남긴다.
- 갱신은 버전을 올리는 UPDATE 한 번으로 한다.
  - 같은 라인에 동시에 상태를 반영하던 쪽은 낙관적 락으로 실패하고 다시 읽는다.
  - 취소 단계 쪽은 충돌로 되돌아가지 않는다. 되돌아가면 이미출고를 다시 불러 400이 난다.
- 이미출고가 400으로 거절된 경우는 그대로 conflict만 남기고 라인을 건드리지 않는다. 거절 이유를 모른다.
- 상태 우선순위 규칙(ADR-0003)은 바꾸지 않는다.

## 검토한 대안
- **재조회 결과에서 클레임이 비어 있으면 지우기:** 재조회는 샵바이 기준이지만, 처리 시점에 이미 오래된 결과일 수 있다.
  - 메시지 지연 때문이다. 단건 조회나 클레임 변경 시각이 없어 새 클레임을 잘못 지울 위험이 있다.
- **대사가 CLAIM_MISMATCH를 자동으로 고치기:** 대사는 탐지만 한다는 설계(4.4)를 바꿔야 한다.
  - 같은 오래된 결과 문제가 있다.

## 결과
- 이미 배송중인 주문의 취소도 이미출고 뒤 우리 라인이 샵바이와 같아진다. 대사 불일치가 0으로 돌아온다.
  - `CancelAfterPickingScenarioTest`에 새 테스트를 넣었다. 수정 전에는 실패하고 수정 후에는 통과한다.
  - `DemoApiScenarioTest`에 출고 후 취소 뒤 불일치 0 확인을 넣었다.
- 샵바이 관리자 화면에서 사람이 직접 클레임을 철회한 경우처럼 우리가 호출하지 않은 철회는 여전히 웹훅·재조회로 지워지지 않는다.
  - 대사가 `CLAIM_MISMATCH`로 드러낸다 (미해결).
