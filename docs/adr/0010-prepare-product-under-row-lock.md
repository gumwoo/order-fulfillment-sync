# ADR-0010 상품준비중 변경은 출고 행 잠금 안에서 한 번만 한다

- 상태: 채택
- 날짜: 2026-11-12

## 맥락
데모 화면에서 주문 50건을 중복 전송 2번, 웹훅 유실 30%로 넣자 미처리 conflict가 1건 생겼다.
- 사유는 `PREPARE_PRODUCT_REJECTED`였다. 샵바이 400 응답, "결제완료 상태가 아닌 옵션".
- 같은 주문옵션을 여러 메시지가 동시에 처리했다. 중복 웹훅은 이벤트 키가 같아 걸러지지만, 웹훅·실패 웹훅·재조회는 출처가 달라 각각 처리된다 (ADR-0001).
- 두 처리기가 모두 우리 DB에서 결제완료를 읽고 상품준비중 변경을 호출했다.
- 먼저 호출한 쪽이 성공한 뒤라 늦은 쪽이 400을 받았다. 실제 상태는 정상인데 사람 처리 목록에 남는다.

- 잠금을 넣은 뒤에도 429 30회와 웹훅 유실을 함께 넣은 데모에서 같은 conflict가 2건 나왔다.
  - 원인은 "반영됐는데 응답을 잃은 호출"로 추정한다.
  - mock은 상품준비중을 반영한 뒤 응답 전에 웹훅을 동기로 보낸다. 부하로 inbound가 느리면 응답이 읽기 타임아웃(5초)을 넘을 수 있다.
  - 그러면 우리 쪽은 실패로 보고 트랜잭션을 되돌린다. 재시도하면 이미 상품준비중이라 400이 온다.
  - 실제 타임아웃이 났는지는 로그로 확인하지 못했다. 다만 실제 샵바이에서도 생길 수 있는 경우다.

## 결정
- 상품준비중 변경 단계를 하나의 트랜잭션에서 진행한다.
  - 출고 행을 잠근다(`SELECT ... FOR UPDATE`).
  - 이미 상품준비중 처리가 끝났으면 호출하지 않는다.
  - 아니면 주문 라인을 다시 읽고, 결제완료이고 클레임이 없을 때만 호출한다.
  - 호출 후 끝났다고 표시한다.
- 호출 결과를 모르면 따로 커밋해 남긴다. 타임아웃, 연결 끊김, 5xx가 여기에 해당한다 (`shipment.prepare_outcome_unknown_at`).
  - 429와 4xx는 샵바이가 처리하지 않은 것이 확실하므로 남기지 않는다.
- 결과를 모르는 호출이 있었던 뒤에 400을 받으면, 앞선 호출이 반영된 것으로 보고 conflict 없이 끝낸다.
  - 실제로 어긋났다면 대사가 불일치로 잡는다 (ADR-0002).
- 처음 호출에서 받은 400은 이전처럼 conflict로 남긴다.
- ADR-0009의 취소 단계와 같은 방식이다.

## 검토한 대안
- **400을 받으면 샵바이에서 실제 상태를 다시 확인:** 단건 조회 API가 없다.
  - 상태 변경 기간 검색으로 찾아야 해서 호출이 늘고 레이트 리밋을 더 쓴다.
  - 경합 자체를 없애지 못한다.
- **처리 중 표시를 CAS로 먼저 기록:** 호출이 실패하면 표시를 되돌려야 한다.
  - 프로세스가 죽으면 표시가 남아 영원히 건너뛴다.

## 결과
- 같은 옵션의 상품준비중 변경은 직렬화된다. 잠금은 호출 한 번 동안만 잡는다.
  - 레이트 리미터 대기가 길어지면 같은 옵션의 다른 메시지가 그만큼 기다린다.
- 결과를 모르는 호출 뒤의 400은 사람에게 보이지 않는다. 그동안 다른 이유로 상태가 바뀌었다면 대사 배치가 드러낼 때까지 늦게 보인다.
- 3PL 출고요청 등록 단계는 여전히 잠금 밖이다. 동시에 처리하면 등록이 두 번 호출될 수 있다.
  - 지금 mock은 같은 주문옵션 재등록을 받아 준다. 실제 파스토의 중복 등록 동작은 미확인이다 (external-facts.md).
