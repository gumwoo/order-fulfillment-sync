# ADR-0006 SQS Standard 큐를 쓰고 FIFO는 쓰지 않는다

- 상태: 채택
- 날짜: 2026-11-11

## 맥락
설계 문서 4.3절과 ADR-0003에서 FIFO 사용 여부와 그룹 키(주문번호 vs 옵션번호)를 미결로 남겼다.
- 순서: ADR-0003이 도착 순서 대신 상태 우선순위로 판정하므로, 수신 순서 보장이 결과를 바꾸지 않는다.
- 중복: ADR-0001이 DB 멱등 키로 막으므로, FIFO 중복 제거(5분)가 필요 없다.
- 지연 재처리: 출고 확정이 송장보다 먼저 오면 메시지별로 N분 뒤에 다시 처리해야 한다(설계 4.8, F-12).
  그런데 FIFO 큐는 메시지별 타이머를 지원하지 않는다(external-facts.md).
- 처리 막힘: FIFO는 같은 그룹의 앞 메시지가 429 대기로 처리되지 못하면 뒤 메시지도 막힌다.

## 결정
- 주문 이벤트 큐는 SQS Standard 큐 하나와 DLQ 하나로 한다.
- 메시지 그룹 키는 쓰지 않는다.
- 같은 주문 라인을 두 소비자가 동시에 처리하는 경우는 `order_line_state.version`(낙관적 락)으로 막는다.
  충돌한 쪽은 메시지를 지우지 않고 다시 받게 한다.

## 검토한 대안
- **FIFO + 주문번호 그룹:** 순서는 보장되지만 복구 경로가 늦게 넣는 이벤트는 어차피 막지 못한다.
  메시지별 지연을 쓸 수 없어 F-12를 별도 큐나 스케줄러로 만들어야 한다.
  한 주문의 옵션들이 직렬 처리된다.
- **FIFO + 옵션번호 그룹:** 동시성은 좋아지지만 위 지연 문제가 그대로 남는다.
- **FIFO 별도 지연 큐(큐 전체 DelaySeconds):** 지연 시간이 큐마다 고정이고 큐가 늘어난다.

## 결과
- 순서와 중복을 모두 소비자 쪽(DB)에서 처리하므로 F-03, F-04 시나리오가 이 결정의 검증이다.
- 처리량 한도는 FIFO 300/s가 아니라 Standard 큐의 한도를 따른다.
- 부하 측정 결과는 측정 후 docs/에 기록한다.
- ADR-0003 결과 절의 "FIFO 사용 여부는 부하 측정 후 정한다"는 측정 대신 위 기능 제약(메시지별 지연 불가)으로 정했다.
