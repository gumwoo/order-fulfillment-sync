# ADR-0009 취소 처리 단계는 행 잠금 안에서 진행하고, 재시도 가능한 순서로 기록한다

- 상태: 채택
- 날짜: 2026-11-11

## 맥락
ADR-0005가 정한 취소·출고 분기를 구현하자 리뷰에서 동시성과 장애 후 재개 문제가 나왔다.
- 같은 취소 건을 메시지 처리기와 주기 작업(배송보류 일괄, 이어 하기)이 동시에 진행하면 단계가 되돌아가고,
  3PL 취소·클레임 승인이 두 번 호출될 수 있다.
- 이미출고를 호출한 뒤 저장 전에 죽으면, 다시 호출할 때 샵바이가 거절해 CS 회수 건이 영영 생기지 않는다.
- 순서가 뒤집혀 늦게 온 취소 신청이 이미 철회·완료된 클레임을 다시 취소하려 한다.
- 배송보류 건별 재시도에서 일시 장애도 영구 실패(HOLD_FAILED)로 처리된다.

## 결정
- 단계마다 하나의 트랜잭션에서 처리한다.
  - 취소 건 행을 잠그고(`SELECT ... FOR UPDATE`) 현재 단계를 확인한다.
  - 외부 호출은 한 번만 하고, 다음 단계를 저장한다.
  - 배송보류 일괄은 `FOR UPDATE SKIP LOCKED`로 잠근 건만 처리한다.
- 피킹 이후 취소는 회수 건과 `RECALL_PENDING`을 먼저 기록하고 이미출고를 호출한다.
- 승인·이미출고가 400이면 "이미 처리됐을 수 있음"으로 보고 conflict를 남긴 뒤 다음 단계로 간다.
  - 무한 재시도 대신 사람이 확인한다.
  - 다른 4xx·5xx는 예외로 두어 단계가 그대로 남고, 다음 시도에서 다시 한다.
- 3PL 취소 거절의 상태가 이미 취소(CANCELED)면 취소 완료로 본다.
- 새 취소 건은 우리 라인의 현재 클레임이 그 취소 신청(같은 claimNo, CANCEL_REQUEST)일 때만 연다. 이미 열린 건은 이어서 진행한다.
- 배송보류 건별 재시도의 처리
  - 5xx는 대기(HOLD_PENDING)로 남긴다.
  - 400이면 3PL 상태를 다시 본다. 피킹 이후면 회수 경로로 가고, 아니면 HOLD_FAILED와 conflict를 남긴다.
- 출고 요청이 3PL에 등록한 직후 클레임이 생겼으면 방금 등록한 3PL 주문을 바로 취소한다.
  - 취소 처리가 "3PL 미등록"으로 먼저 끝난 경합을 막는 것이다.

## 검토한 대안
- **CAS 갱신(`update ... where state = :expected`)만 사용:** 단계 역행은 막지만 외부 호출 중복은 못 막는다.
  두 쪽이 같은 단계를 읽고 둘 다 호출한 뒤 한쪽만 저장에 성공한다.
- **분산 락(Redis):** 행 잠금으로 충분하고 DB 하나로 끝난다.

## 결과
- 외부 호출이 잠금 안에서 일어나므로 같은 건의 처리는 직렬화된다. 건마다 수 초 이내라 처리량 영향은 작다.
- 외부 호출 성공 후 저장 전 장애는 여전히 재호출을 부른다. 재호출 결과가 400이면 conflict로 드러난다.
- 이미출고로 클레임이 철회됐는데 샵바이 주문 상태가 이미 배송중이라 앞으로 가지 않으면, 웹훅만으로는 우리 쪽 클레임 정보를 지우지 못한다.
  - 이 경우는 대사 배치가 CLAIM_MISMATCH로 드러낸다.
  - 우리가 호출한 이미출고에 대해서는 [ADR-0012](0012-apply-already-delivery-result.md)로 해결했다.
