## 1. 장애 주입 종합 (주문 300건)

넣은 장애는 다음과 같다.
- 웹훅 30% 유실: 앞 150건 구간은 샵바이 실패 내역에 남기고, 뒤 150건 구간은 흔적 없이 버렸다.
- 웹훅 2회 중복 발송
- 샵바이 429 50회, `EXHAUSTED` 헤더 50회

흐름은 다음과 같다.
1. 결제완료 웹훅
2. 3PL 출고요청과 샵바이 상품준비중
3. 복구 경로(실패 웹훅 조회 → STATUS_CHANGE 재조회)
4. 3PL 출고완료·송장
5. 송장 반영

| 지표 | 실측값 |
|---|---|
| 웹훅 발송 / 버림 | 692건 / 159건 |
| 복구 전 불일치 (대사 배치 기준) | 159건 |
| 복구 전 3PL 출고요청까지 간 주문 | 205 / 300 |
| 실패 웹훅 복구 후 불일치 | 30건 |
| STATUS_CHANGE 재조회 후 불일치 | **0건** |
| 복구 시간 (복구 시작 → 불일치 0) | 14.7초 |
| 복구 후 3PL 출고요청까지 간 주문 | 300 / 300 |
| 경로별 반영(APPLIED) | 웹훅 711, 실패 웹훅 경로 159, 재조회 경로 30 |
| 경로별 중복 차단(DUPLICATE) | 웹훅 764, 실패 웹훅 경로 141, 재조회 경로 270 |
| 샵바이 레이트 리밋으로 재발행 | 53회 |
| 샵바이 1초 최대 호출 | 34회 (한도 80) |
| DLQ | **0건** |
| 송장 반영 | 300건, by-shipping-no 요청 3회, 17.4초. 최종 불일치 0건 (아래 "재측정" 참고) |
| 출고완료가 송장보다 먼저 와서 지연 재처리 | 296회 (포기 0건, conflict 0건) |
| 같은 옵션에 3PL 등록 요청이 2번 이상 간 경우 | 3건 |

### 해석
- 흔적 없이 버린 구간의 유실은 실패 웹훅 조회로는 되찾을 수 없다. 그 30건은 STATUS_CHANGE 재조회가 되찾았다.
  - 두 복구 경로가 모두 필요하다는 근거다 (ADR-0002).
- 웹훅 중복과 복구 경로의 겹침으로 생긴 중복 1,175건(764 + 141 + 270)은 모두 멱등 키에서 걸러졌다 (ADR-0001).
- 3PL 등록 중복 3건은 웹훅과 복구 경로가 같은 결제완료를 거의 동시에 처리한 경우로 보인다(원인은 추정이다).
  - mock 3PL은 주문옵션번호 기준으로 멱등이라 주문이 중복 생성되지는 않았다.
  - 실제 3PL이 중복 등록을 어떻게 처리하는지는 확인하지 못했다.

## 3. 웹훅 수신 부하 (k6)

- k6 v2.1.0, 동시 사용자 20, 30초
- 요청마다 CHANGE_ORDER_STATUS 원소 5개
- 출고 연동은 끈 상태(반영만)

| 지표 | 실측값 |
|---|---|
| 요청 수 / 실패율 | 7,768건 / 0% |
| 처리량 | 258.6 요청/초 (원소 약 1,293건/초) |
| 응답 시간 | 평균 76.8ms, p50 45.9ms, p95 108.4ms, p99 531.2ms, 최대 7,219ms |
| 반영 완료 (원소) | 38,840 / 38,840 |
| 부하 종료 후 반영 완료까지 | 191.4초 |
| DLQ | 0건 |

### 해석
- 수신(원본 저장 + outbox)은 반영보다 빠르다. 30초 동안 받은 원소 38,840건을 반영하는 데 부하 종료 후 191초가 더 걸렸다.
  - 이 구성(worker 1개, 소비 스레드 4개)에서는 반영 쪽이 병목이다.
  - 수신을 즉시 끝내고 처리를 분리한 설계(설계 4.1) 덕분에, 밀린 처리가 수신 응답 시간에 그대로 옮겨 가지 않았다.
- 최대 응답 7.2초 원인은 확인하지 못했다. 일부 요청에서 발생했고, 같은 PC에서 DB 컨테이너를 함께 쓴 영향일 수 있다(추정).

ADR-0010~0012(상품준비중 행 잠금, 응답을 잃은 호출, 이미출고 반영)를 넣은 뒤 같은 측정을 다시 돌렸다.
같은 PC지만 전날과 상태가 달랐다(블루스크린으로 재부팅 뒤, IDE 등이 떠 있어 남은 메모리 약 1.2GB).
코드 탓인지 환경 탓인지 가르려고 이전 버전(`2dd2a54`)도 같은 PC에서 번갈아 돌렸다.

### 성능 지표: 다시 재야 한다

- 이날 PC 상태로는 같은 이전 코드도 실행마다 크게 흔들렸다. 그래서 성능 수치는 결과로 싣지 않는다.
  - 원래 수치는 progress.md 2026-11-12 (14)에 기록으로만 남겼다.
- 1절의 성능 수치(처리량, 시간)는 2026-11-11 PC 상태의 값이다. ADR-0010~0012 뒤에는 아직 다시 확인하지 못했다.
- 행 잠금(ADR-0010)은 같은 옵션을 동시에 처리하는 소비 스레드를 잠금 동안 기다리게 한다.
  - 이론상 중복이 많을 때 처리량을 낮출 수 있다. 확인하지 못했다.
- 재부팅 직후 다른 프로그램 없이 여러 번 돌려서 다시 잴 예정이다.

### 측정 코드에서 고친 것
- 송장 단계에서도 mock의 웹훅 30% 유실이 계속된다.
  - 배송중 변경 웹훅은 송장 요청 1번(100건)마다 하나씩 나간다. 이것이 버려지면 그 100건이 우리 쪽에서 배송중이 되지 않는다.
  - 예전 측정은 송장 반영 직후 바로 대사해서 "최종 불일치"가 운에 따라 0, 100, 200으로 달랐다.
    - 2026-11-11의 0은 세 웹훅이 모두 살아남은 경우다. 확률은 약 34%다.
  - 이제는 송장 직후 값(`mismatch_afterInvoice_beforeRecovery`)과 재조회로 복구한 뒤 값(`mismatch_final`)을 따로 남긴다.
- 수신 부하 측정은 30초마다 진행을 남긴다. 10분 안에 다 반영되지 않아도 그때까지의 반영 수를 기록한 뒤 실패한다.
  - 첫 재측정에서 한 번 10분을 넘겼다. 같은 조건으로 두 번 더 돌리자 171초, 180초에 끝났다. 원인은 확인하지 못했다.
